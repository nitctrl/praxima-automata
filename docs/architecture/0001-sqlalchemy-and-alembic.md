# ADR 0001: SQLAlchemy 2.0 for data access and Alembic for migrations

- Status: **accepted** (2026-09-26)
- Supersedes: the "no ORM, parameterized SQL only" rule in the first version of `CLAUDE.md`

## Context

Until now the backend talked to Postgres with hand-written SQL through psycopg. Migrations
were plain SQL files in `supabase/migrations/`, applied by the custom runner
`scripts/database.py`. That fit a voice agent that reads one published snapshot per call.

The product is growing into:

- a full **REST API** (`/api/v1`) over many resources (workspaces, agents, entities,
  documents, announcements, work items, conversations, memberships), and
- **CRM features**: contacts, leads and requests with pipeline stages, tasks, assignees,
  history, plus sync with external CRMs.

That means hundreds of create/read/update/list queries with filtering, sorting, paging and
relations. Writing and maintaining all of them by hand is slow and error-prone. The new data
model (`docs/database/database-schema.md`, about 40 tables in 10 schemas) also needs a
migration tool that is standard, reviewable and CI-friendly.

## Decision

1. **SQLAlchemy 2.0 (async)** is the data-access layer for new code, running on the existing
   **psycopg 3** driver (`postgresql+psycopg://`).
2. **Alembic** manages the schema of the new, vendor-neutral database. Revisions live in
   `db/migrations/versions/` and are numbered `NNNN_description.py`.
3. **ORM models are infrastructure.** Each module keeps its tables in
   `modules/<module>/infrastructure/models.py`. Domain code stays pure (Pydantic or
   dataclasses) and never imports SQLAlchemy. Repositories translate between the two.
4. **Postgres features that Alembic cannot autogenerate are written as SQL inside
   revisions** (`op.execute`): RLS policies, `SECURITY DEFINER` functions, triggers,
   exclusion constraints, partitions, grants. Autogenerate is a first draft that is always
   reviewed; it is never trusted blindly.
5. **Tenant scoping is unchanged.** Every tenant transaction runs
   `set_config('app.workspace_id', …, true)`, the same as `SET LOCAL`, through one helper
   (`praxima.shared.db.engine.tenant_transaction`). RLS in the database remains the real
   isolation boundary.
6. **Hot paths may use SQLAlchemy Core or `text()`** (for example the voice runtime's single
   release read) when the ORM adds nothing.
7. **Migrations are forward-only.** `downgrade()` refuses; fixes ship as new revisions. Unsafe
   locking patterns are caught with **squawk** in CI on the SQL that Alembic generates
   (`alembic upgrade --sql`).

## Consequences

**Positive**
- Much less repetitive code for CRUD, filtering and paging. Typed models; relations
  expressed once.
- Autogenerated migration drafts, a standard CLI and a standard CI story. Widely known, so
  easier hiring and onboarding.
- One driver (psycopg 3) for all code.

**Negative / risks**
- An extra abstraction to learn. Lazy loading can cause N+1 queries → use `selectinload`
  and explicit queries, and review query counts in tests for list endpoints.
- ORM sessions must never leak across tenants → sessions are short-lived, one per request
  or job, always opened through `tenant_transaction`.
- Two migration systems exist during the transition: `supabase/migrations/` (current,
  frozen) and `db/migrations/` (target). The target is always an **external** PostgreSQL
  16+ (a local install or Supabase, never Docker) reached through `DB_OWNER_DATABASE_URL`.
  Alembic only touches the module schemas, never the legacy `public` schema.

## Alternatives considered

| Option | Why not |
| --- | --- |
| Keep plain SQL + custom runner | Fine for the voice agent; too much hand-written CRUD for a REST API and CRM |
| Plain SQL + dbmate or Atlas | Standard runner, but still hand-written queries everywhere |
| Django ORM | Would bring a second web framework next to FastAPI |
| SQLModel | Thin layer on SQLAlchemy; mixes API schemas with table models, against our layering |
